# 因子挖掘：创意来源模块

入口为主命令 `crypto-quant factor-mine`，也可以运行 `python -m crypto_quant.research.factor_mining`。代码、研究记录和创意卡都在量化投资主项目内；MASFactorMiner仅作职责设计参考。

## 文件职责

| 文件 | 输入 → 输出 |
|---|---|
| `contracts.py` | 显式研究选择、模型字段提取、候选及检验设计 → 经校验的合同与定义 |
| `model.py` | 单次OpenCode Go请求 → 回复、原始返回及usage，或带诊断的API错误；支持chat/messages |
| `records.py` | 全部证据 → 实际模型上下文、按需原文读取、逐次请求档案、最多5次API重试及最多2次回复纠正 |
| `workflow.py` | 构想→核对/修复/计算→评估→候选去向决策→按需优化；保留批次→B验证→创意卡 |
| `evaluation.py` | 公式值与独立标签 → 四类结果、配对修改检验、整批BH/BY校正 |
| `reporting.py` | 真实程序结果和单独模型解释 → Markdown报告、分组收益SVG图 |
| `cli.py` | 显式合同与逐小时币池 → 本地数据加载及上述流程 |

四个Agent是四种受限职责和提示词，通过同一模型接口调用。公式计算、统计、预算、数据边界和版本校验由程序执行。

## 候选决策与分流

优化角色先输出`decisions`，为本轮全部候选及此前继续优化的候选回答`research_basis`、`modification_hypothesis`、`verifiable_improvement`、`attempt_value`四个问题。各问题包含明确布尔判断和理由；研究现象由模型分析，不硬编码穷举。`evidence_refs`须引用现有记录，并至少包含当前候选的程序结果，保留／优化还须引用其评估记录。

`disposition`为`optimize`、`retain`、`pause`、`discard`。`continue_optimization`单独记录，因此`retain`可同时优化；暂停、淘汰禁止优化，暂停须写恢复条件。计算失败不能单独支持淘汰。所有决定均为模型研究判断，引用校验不等于理由已被证明。

只有四问均支持、预算允许且提供完整检验方案，才允许继续。每条proposal还必须回答：原核心假设是什么、公式修改如何更好表达或检验它、什么配对结果表示修改没有帮助。三项说明是待检验的研究主张；程序只检查字段完整、版本和实验关联，不把文本当作假设已经成立的证据。每条proposal必须对应本轮明确授权的候选；下一轮不能从未授权的父版本生成改进版。此前仍优化的原版会与本轮新版本一起重新判断；其他候选保留历史但不自动重启。无建议则结束循环。

最终状态写入`a-complete.json`的`candidate_decisions`和`retained_ids`，报告展示依据及恢复条件。冻结入口只接收`retain`候选，并将A决策随证据存入冻结批次及最终创意卡。B数值门槛和主项目交接边界保持原合同。旧运行的代码指纹检查仍严格执行，新流程使用新运行ID。

角色输出通过提示词中的JSON Schema明确字段、类型及必填项，程序继续严格检查，不将字符串布尔值自动转换。计算Agent必须返回并匹配当前`candidate_id`。这不是提供商原生约束解码的保证，返回结果仍可能被格式校验拒绝。

评估角色只提供`analysis`、`mechanism`、`conditions`、`falsifiers`、`limitations`、`next_steps`六项解释，不输出候选去向。四个角色统一通过`AgentGateway`接收，`model_fields`按声明的对象、数组、标量及可空字段递归提取；额外字段（含旧`decision`、内层重复`read_records`）不参与执行，必需字段缺失和类型错误仍报错。枚举、数量、预算、版本、证据及语义条件继续由原业务校验执行。

外层`result/read_records`与原文读取请求也采用同一规则。每次`format_deviation`记录角色、额外字段JSON指针和原始回复位置，ID为`model-<call>-format`。原文保留在`model_calls`；后续记录与原文读取的继续消息只传提取后的字段，不重新发送附加字段的值。A／B报告展示全角色格式偏差。核心字段和研究判断不符进入下述回复纠正流程；研究合同、数据接口与冻结哈希检查不放宽。

## 时间与数据合同

- 输入索引 `t` 是小时K线开盘标签，行内容至 `t+1h-1ms` 才可用。
- 首版标签 `perp_next_open_24h` 使用 `perp_open[t+25h] / perp_open[t+1h] - 1`。例如10:00那根K线结束后，以11:00至次日11:00的永续开盘价计算24小时收益。没有把下一根小时收益当24小时收益。
- A/B/C边界为UTC整点、左闭右开。样本收益终点等于或超过下一段起点时排除；按小时评估时末尾25条小时观察被排除，因为标签还有下一小时开始的等待。报告保存实际排除小时数和资产观察数。
- A读取截止B前一小时，B读取截止C前一小时，C没有因子挖掘读取入口。预热记录只用于计算，不作为更早阶段的评估样本。
- 因子字段只来自共享35字段合同，标签独立存放。币池必须显式逐时给出，不从今天的30币名单反推历史。
- 整段都为false的资产不请求数据，返回明确的非成员状态和空值；曾在该面板内成为成员的资产保留入池前时序预热。A/B可以使用同一资产全集，尚未上市资产此前为false。
- 冻结B批次时保存候选实际公式、含义、方向、统计规则、B成员资格哈希、A证据哈希、代码和运行环境指纹。B预热成员资格与已记录的A历史保持一致。

正式研究的日历日期、历史币池生成规则及既往数据使用审计仍需在合同中完成。代码支持执行该合同，不代替这些事实核查。

## 计算含义与修改范围

共享表达式编译器从实际展开语法树提取字段、市场、单位、子步骤引用、窗口、当前期使用与截面范围。计算Agent必须核对六个维度，保留逐项原文依据、实际步骤及判断。

初次表达式与修复表达式都经过同样检查。定义不足返回构想；改变含义创建新候选ID并关联父版本；修复不覆盖原始定义。跨资产排序的最终输出不能带基础币单位。

优化建议先交回构想，逐条沿用／调整／放弃。构想Agent采用或调整建议前，核对候选公式是否符合建议声明的核心假设与公式一致性说明；调整时把这项研究判断写入处理理由。相同假设下可联动修改多个公式位置，不按窗口、平滑等类别或单一语法差异限制。程序仍执行表达式白名单、数据和时间边界、父版本与proposal关联、固定方向及预算检查。改变方向不属于该次受控优化。

对照与新候选在相同时间网格、共同有效资产上重新排名和分组，计算配对改善及其不确定性。最低改善和允许IC损失在结果之前记录。上限仍达不到目标则停止，下限达到目标且满足损失限制则支持继续，无法区分则证据不足暂停。预算用尽单独记录；重启须关联旧路线并声明新增依据。假设与公式是否一致仍由Agent作研究判断，实际配对结果才检验修改是否帮助。

## 统计实现

- 横截面Rank IC使用平均并列排名。分组采用等宽排名分位区间、组内等权；相同因子值保持同组，缺组时不伪造收益差。
- 保留全部逐期、滚动和固定阶段结果，以及每个标的的有效样本概况。ICIR与组间差的均值/样本标准差均不年化。
- 均值置信区间及双侧检验采用Newey-West/Bartlett HAC、截距模型的小样本校正与渐近正态近似。lag由合同显式声明，至少覆盖重叠预测窗口；缺失期保留在原时间网格，不压缩间隔。常数或不足样本返回不可估计状态，不生成虚假的显著性。
- B批次所有候选的IC和有向组间差两项主要检验构成统一校正范围。无法估计的检验保留在范围内，原始p为null，校正时按1处理。BH/BY和目标水平显式固定。
- B数值验证同时要求整批校正支持、固定方向的IC与收益差达到预定幅度、至少两个有效阶段达到预定重复比例。程序先记录`validation_result`（通过状态、程序判定来源、交付资格、原因和检验），再让评估Agent解释。报告须完整，但模型的保留／淘汰意见不再作为准入条件；工程样例不能入池。
- 创意卡关联`a_research_decision`、`b_validation_status`及程序生成的`admission_evidence`。B数值通过与允许交付分别记录，完整策略验证状态仍为`not_started`。B未通过不会自动变成A段优化任务。
- A段的自适应搜索和修改比较始终标为开发证据。分组未来收益不是含成本策略净值。

统计方法参考：[HAC文档](https://www.statsmodels.org/stable/generated/statsmodels.stats.sandwich_covariance.cov_hac.html)、[多重检验文档](https://www.statsmodels.org/stable/generated/statsmodels.stats.multitest.multipletests.html)。实现只使用现有NumPy/Pandas及标准库，不新增statsmodels依赖；HAC用独立的Bartlett矩阵计算作测试对照。

## 跨轮上下文与原文读取

每次请求读取全部A记录，包含定义、失败、修复、完整数值评估、模型报告、建议处置与实验决定。没有Top5、最近30条或固定200字符裁剪。请求的原始消息实际写入`model_calls/*-request.json`。

当前尚未绑定Go各模型的专用分词器，使用UTF-8字节数作保守输入token上界；响应usage另行保留。用户已要求取消人为单次输出上限，当前示例合同`output_tokens=null`，请求省略`max_tokens`，由服务使用默认输出设置。此时本地`context_tokens`只用于输入上下文管理；合同明确指定输出数值时才预留对应容量。服务端自身的容量限制仍适用，省略参数不保证无限输出。输入上界不是供应商的精确token数，可能较早触发数值分页。

完整请求超预算时，相同字段覆盖统计作无损合并，长数值表替换成原文位置与总行数，模型可以用`read_records`请求任意记录的JSON指针和页码。定义、失败、修复依据、模型分析与决定保持原文。读取结果作为实际后续消息送入模型，所有请求均保留调用档案，不设总调用次数上限；上下文仍超容量则停止并保留证据，不继续静默删减。

B有独立记录目录，只开放评估角色，不反馈给A构想或优化。B访问开始前即留痕；一次验证中断也不会自动重跑B。

## OpenCode Go与运行限制

已适配直接Go API的chat/messages请求、服务要求的独立User-Agent和稳定`x-opencode-session`。密钥在运行时优先从指定环境变量读取，未设置时读取当前项目目录的`.env`同名项。支持单行裸值或成对引号，不做变量展开，不执行文件内容；空值、重复项和错误引号会报错，错误消息不回显密钥。密钥与请求头不写入证据。模型路由参考[Go官方文档](https://opencode.ai/docs/go/)；`responses`路由模型暂未适配，不应选用该路由的模型ID。

同一次API请求允许首次调用后最多重试5次（合计至多6次），由`AgentGateway`计数和留痕。可重试错误包括连接失败／超时、HTTP 408／429／5xx、服务响应JSON或结构损坏，以及正常／长度结束标志下的空正文。鉴权或参数等其他HTTP错误、内容过滤不自动重试；非空截断及模型正文JSON／角色格式／研究约束错误进入独立的回复纠正流程。模型、参数、消息、会话ID保持一致，重试前依次等待1／2／4／8／16秒。

每次尝试都生成独立`*-request.json`；重试请求记录`attempt`和`retry_of`。已取消总调用次数上限，合同不再包含`max_model_calls`。API失败的`*-error.json`记录是否重试、等待时间及停止原因；空正文也先保存`*-response.json`中的原始返回、结束标志和usage，再决定重试。网络错误只记录类型，响应中已知密钥脱敏，请求鉴权头不写入档案。

重试只重发当前API请求，不重跑已完成的构想、计算、评估或B数据加载。暂时性API错误耗尽重试后，计算核对失败记录到当前候选，解释失败记录为待补；构想／优化失败仍停止探索。不可重试错误明确停止，不自动切换模型。

2026-09-14已通过Go调用DeepSeek V4.1 Flash完成两轮工程联调，使用`chat`、显式`reasoning_effort=low`、100万上下文预算及16384单次输出上限。高推理强度曾耗尽输出上限；一次最终空正文响应通过明确的单次收尾调用完成，记录中标为`manual_finalization`。原始自动流程停止记录保留。模型设置写入运行目录，回复保留请求的推理强度和usage；空正文失败的原响应未保留usage，因此不能精确汇总全部消耗。

该样例未开展正式B验证，不能证明因子具有独立预测能力；其他模型／推理设置、流式服务兼容性和专用分词器仍需另行验证。记录中的`scripted-fixture`表示此前离线测试回复，`deepseek-v4.1-flash`表示本次真实请求。详见[真实联调记录](../../../../experiments/factor_mining/go_deepseek_v41_flash_20260914_low/real-model-verification.json)。

## 回复纠正、候选隔离与报告补全

每次角色任务首次收到无效回复后，最多提供2次纠正机会。非空截断（`length/max_tokens`）、无效JSON、必需字段／类型错误、语义矛盾、错误证据引用及预算不符的研究建议均可纠正。原文保存在`model_calls`；`invalid_model_response`记录错误、纠正序号和是否继续。纠正消息提供原任务与错误原因，不把未接受回复中的附加字段重新发给模型。原文读取ID／路径／分页参数错误也能纠正；证据被篡改、文件异常或内部程序错误不会作为模型格式问题吞掉。

业务校验在提交状态前执行。无效构想或优化回复不会占用候选ID、建议ID或路线尝试次数。纠正与API重试不受总调用次数限制，不改变模型、研究合同或输出上限。超过纠正次数后，构想／优化任务停止；计算Agent记录`model_review_failed`并跳过当前候选，评估Agent记录`report_pending`，其他候选继续。上下文不足时，解释也记录待补。轮数、候选数量及路线尝试限制保持原合同设置。

A段优化Agent可根据已完成数值和明确记录的解释缺口决策，但冻结入口要求所选保留候选已有合格解释。`a-complete.json.pending_report_ids`是探索结束时的快照；后续补全结果以命令返回及重新生成的`A-report.md`为准。原始记录和完成快照不覆盖。A报告只能在冻结B之前补全，不重开构想或优化。

B段先完成全部数值计算、批次校正与逐个程序判定，保存带哈希的`b-numerical-complete.json`，再生成解释。单份解释失败不会阻断其他解释，也不丢弃数值结果。返回`status=reports_pending`和缺失名单；只有全部解释就绪才生成最终`validation.json`。创意卡按各候选程序资格和解释完整性独立交付。

`factor-mine complete-reports --run-dir <运行目录> --stage A或B --model <模型ID> --protocol chat或messages`仅补缺失解释。无需`--db`或`--universe`，不加载行情、不重算公式或统计；补全不受累计调用次数限制。B补全须通过代码／合同／冻结A证据／完整B数值快照校验；没有完整B数值快照的运行不能使用此入口。重复补全跳过已有解释，已有创意卡须与证据一致，不重复生成；仅可重建派生Markdown报告。

旧代码指纹的运行仍拒绝打开；旧合同用于创建新运行时需移除`max_model_calls`字段，历史合同和失败记录保留供查阅。调用次数限制已取消，单个任务仍最多纠正2次、单次API请求仍最多重试5次。
